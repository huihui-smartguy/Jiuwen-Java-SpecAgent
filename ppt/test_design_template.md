# 开发串讲文档模板

> 目标：让评审人快速判断方案是否合理、边界是否清楚、约束是否明确、测试是否能覆盖。默认只保留基础必填内容，复杂功能和示例放到附录。

本节用于对齐“为什么做”和“做到什么程度算完成”。只写和本次开发直接相关的背景，不展开无关历史。

## 2. 场景、规则与约束

## 3. 总体方案

本节用于说明“方案整体怎么工作”。先讲链路和模块分工，不急着展开每个函数或类。

### 方案概述

用 3 到 5 句话说明整体方案：

1. 入口是什么：
2. 核心处理在哪里：
3. 数据如何读写：
4. 如何对用户或下游生效：

### 链路图 / 流程图

### 条件补充项

| 条件 | 建议补充内容 |
|---|---|
| 有复杂数据结构或持久化变更 | 详细数据模型、默认值、索引、兼容性 |
| 有复杂 API / RPC / 消息协议 | 详细接口文档、字段示例、错误码 |
| 涉及旧数据、历史配置、存量用户 | 兼容策略、默认值、迁移影响 |
| 需要灰度、开关或分批发布 | 开关名称、默认值、生效范围、关闭方式 |
| 需要 migration 或批量修复数据 | 执行时机、幂等性、失败恢复 |
| 存在不可逆数据变更或高风险配置 | 回滚方案、影响范围、人工确认点 |
| 涉及权限、多租户、敏感字段 | 权限规则、隔离策略、脱敏要求、审计日志 |
| 涉及异步、缓存、重试、最终一致性 | 状态流转、重试策略、同步 SLA、排障方式 |

### 示例填法

<details>
<summary>背景、目标、非目标示例</summary>

```text
背景：
- 当前问题：批量任务提交后，用户无法区分“已提交”和“已开始执行”。
- 影响范围：任务列表、任务详情、失败重试和客服排障。
- 需求来源：任务中心体验优化需求。

目标：
- 用户提交任务后，系统返回可追踪的任务 ID。
- 任务状态能从“已提交”流转到“执行中 / 成功 / 失败”。

非目标：
- 本次不改造任务调度算法。
- 本次不支持跨租户任务迁移。
```

</details>

<details>
<summary>场景、规则与约束示例</summary>

```text
核心场景：
| 场景 | 触发条件 | 预期结果 |
|---|---|---|
| 提交任务 | 用户上传文件并点击提交 | 系统创建任务并返回任务 ID |
| 查询任务 | 用户打开任务详情 | 展示当前状态、失败原因或完成结果 |

关键规则：
| 规则 | 说明 |
|---|---|
| 状态只允许向前流转 | submitted -> running -> success / failed |
| 同一文件重复提交 | 命中幂等键时返回已有任务 ID |

关键约束：
| 约束 | 说明 | 影响 |
|---|---|---|
| 权限边界 | 用户不能查看自己无权限访问的任务 | 所有查询接口必须校验归属 |
| 兼容旧任务 | 存量任务没有幂等键时仍可查询 | 查询逻辑需兼容空幂等键 |
```

</details>

<details>
<summary>总体方案示例</summary>

```text
方案概述：
1. 入口是任务提交 API。
2. 核心处理在任务服务中完成参数校验、任务创建和状态初始化。
3. 任务数据写入数据库，执行事件投递到队列。
4. 用户通过任务详情 API 查询状态和结果。

模块分工：
| 模块 | 职责 | 输入 | 输出 |
|---|---|---|---|
| API 层 | 参数校验和鉴权 | 用户请求 | 标准响应 / 错误码 |
| 任务服务 | 创建任务和维护状态 | 任务参数 | 任务 ID / 状态 |
| Worker | 执行任务 | 队列消息 | 执行结果 |
```

</details>

<details>
<summary>接口与配置示例</summary>

```text
接口说明：
| 接口/调用 | 类型 | 调用方 | 入参要点 | 字段约束/默认值 | 出参/事件 | 错误或异常 |
|---|---|---|---|---|---|---|
| POST /tasks | HTTP | 前端 | 文件 ID、任务类型 | 文件 ID 必填；任务类型默认 async | task_id、status | 参数非法、无权限、重复提交 |
| GET /tasks/{id} | HTTP | 前端 | task_id | task_id 必填 | status、result、error_reason | 任务不存在、无权限 |

配置说明：
| 配置项 | 所在位置 | 默认值 | 生效时机 | 影响范围 | 回滚/关闭方式 |
|---|---|---|---|---|---|
| task.retry.max_count | 配置中心 | 3 | 下次任务执行 | Worker 重试次数 | 调回旧值 |
| task.upload.max_size_mb | 配置中心 | 100 | 下次请求 | 任务提交 API | 调回旧值 |
```

<summary>测试建议示例</summary>

```text
建议测试重点与开发自测门禁：
| 前置/触发条件 | 建议测试重点 | 希望保证的结果 | 优先级建议 | 建议测试方式 | 是否开发自测门禁 |
|---|---|---|---|---|---|
| 用户具备提交权限且参数合法 | 提交任务 | 返回 task_id，状态为 submitted | P0 | 集成测试 | 是 |
| 同一幂等键重复提交 | 幂等规则生效 | 返回同一个 task_id，不新建任务 | P0 | 单测 / 集成测试 | 是 |
| Worker 执行失败 | 失败状态落库 | 状态为 failed，并记录 error_reason | P1 | 集成测试 | 否 |

关键异常与边界：
- 上传文件超过大小限制时，应返回明确错误。
- 无权限用户查询任务时，不能看到他人任务结果。
- 队列投递失败时，任务不能被误标记为执行中。
```

</details>

## 最小可接受版本

本节用于提醒填写底线。时间有限时可以不填附录，但不能缺少下面这些基础内容。

如果时间有限，至少填写：

1. 背景与目标
2. 核心场景、关键规则与约束
3. 总体链路图
4. 关键设计
5. 可观测性
6. 测试建议

缺少这些内容时，串讲容易退化成“代码改动说明”，评审人难以判断方案是否完整。
